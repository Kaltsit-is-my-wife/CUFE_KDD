# [002] 探针设计：Agent 交互间语义漂移是否显著存在

> 本文件只描述**探针（probe）**，即方法开发之前的现象验证。正式方法实验在探针通过后另起。
> **对应用户原始设想**："跑跑探针看看是否显著"——本文件把它拆成三个有序问题，并对"是否该租服务器"给出明确判断。

## 0. 设计原则（来自对本组 DriftHunter 的批评）

| 原则 | 来源 | 在本探针中的体现 |
|---|---|---|
| 不要用退化的合成数据 | DriftHunter 的随机拼接导致任务自我简化 | 自建轨迹必须注入**语义层**漂移，并有"表层话题不变但目标已偏"的对照 |
| 必须内置最强简单基线 | DriftHunter 缺少"只看相邻两句"的对照 | P3 与后续方法期一律包含**相邻轮基线** |
| 先验证弱点是否真实存在 | `001/notes.md` 调研 #3 的选型逻辑 | 整个 `experiment.md` 就是这条原则的执行 |
| 区分观察/解释/未验证 | 本仓库规则 7 | 每个探针的产出强制分成三段记录 |

## 1. 探针总览

**三问按顺序执行，前一个不通过就不做下一个。**

| 编号 | 问题 | 门槛/产出 | 不通过的后果 |
|---|---|---|---|
| **P1** | agent 交互轮能否定义**可稳定标注**的语义原子？ | Cohen's κ **≥ 0.6** | **方向终止**，标记 `archived` |
| **P2** | agent 之间的漂移是否**显著存在**？ | 发生率显著高于置换零分布（p < 0.05），且效应量可报告 | 现象不存在，无检测器需求 |
| **P3** | 漂移能否**仅从可观测信道**检出？ | 弱监督上界 F1 明显高于随机（给出具体数字即可，不设硬门槛） | 说明需依赖额外信号，影响方法可行性但不必然终止 |

## 2. P1：语义原子本体与标注一致性（go/no-go）

### 2.1 为什么先做这个

DriftHunter 的方法建立在 ATIS/MultiWOZ 的闭集 intent/slot 本体之上。**agent 交互没有这个本体**——这是原方法无法直接迁移的结构性障碍。若本体不可靠标注，后续所有指标都是噪声。

### 2.2 候选语义原子本体（把 slot 重定义为 agent 可观测原子）

| 原子 | 定义 | 取值示例 | 与 DriftHunter slot 的对应 |
|---|---|---|---|
| `role` | 本轮该 agent 实际扮演的角色 | planner / coder / critic / executor | 新增（DriftHunter 无） |
| `goal-atom` | 本轮推进的最小目标单元 | "确定 API 版本" | ≈ intent |
| `tool-action` | 本轮的原子动作或工具调用 | `search(x)` / `write_file(y)` | ≈ slot 的动作位 |
| `commitment` | 对前序承诺的承接/撤销 | uphold / revoke / new | 新增 |
| `constraint` | 本轮生效的约束（授权、禁止项） | "不得写入 prod" | ≈ slot 的约束位 |

### 2.3 标注协议

- **样本**：随机抽取 N 段 agent 交互轨迹（N 由初步预算定，建议**先做 100 轮**的预实验）
- **标注者**：**≥ 2 名人工标注者独立标注**（**关键：不能用 LLM 判自己**，见 `README.md` §9 评估风险）
- **流程**：预标注 → 讨论对齐定义 → 重新标注 → 计算一致性
- **指标**：每个原子分别计算 **Cohen's κ**；报告**逐原子的 κ**，不只报总分（总分会被高一致性的原子掩盖）

### 2.4 否决规则

- **任一关键原子（`goal-atom` / `constraint`）的 κ < 0.6** → 本体不成立 → **方向终止**
- 非关键原子 κ < 0.6 → 可合并或降级为可选字段，**不单独否决方向**

### 2.5 产出（严格分三段记录）

1. **观察**：每个原子的 κ 值、分歧案例的分布
2. **解释**：分歧集中在哪类交互（哪些框架/拓扑/任务）——**这是解释，不是结论**
3. **未验证因素**：标注者是否熟悉该框架；原子粒度是否过细

## 3. P2：漂移发生率的显著性检验

### 3.1 漂移真值从哪来

三种来源，**独立使用并互相对照**（避免自洽污染）：

| 来源 | 优点 | 风险 |
|---|---|---|
| **A. 自建 LLM 轨迹 + 可控注入** | 有真值、可调难度 | 生态效度可能被质疑 |
| **B. 公开框架日志**（CAMEL / AutoGen / MetaGPT / ChatDev） | 真实、有代表性 | 无漂移标签，需人工标注子集 |
| **C. 人工标注子集** | 最可靠 | 成本高，只能做抽样锚点 |

**建议主干 = A，抽检锚 = C，生态加分 = B。** 三者交叉，任何两个一致的结论才写进结论段。

### 3.2 漂移的操作定义

沿用 DriftHunter 的形式化，但把 intent 换成语义原子：

> 设某 agent 在轮次序列上，第 $k$ 轮之前 `goal-atom` 稳定为 $g$，第 $k+1$ 轮变为 $g' \neq g$，且**该变化未被任务分配或显式指令触发**，则定义第 $k$ 轮发生一次漂移 $o_k = 1$。

**关键限定**："未被任务分配或显式指令触发"——排除正常的任务推进，只保留**非预期**偏移。这是与"正常换任务"的边界，必须在标注协议里写死。

### 3.3 零模型（null）——**这是"显不显著"的核心**

不能直接说"漂移率 30% 所以很严重"，必须与零模型比：

| 零模型 | 构造方式 | 检验什么 |
|---|---|---|
| **置换零分布** | 在轨迹内**打乱轮次顺序**（保持边际分布），重算漂移率，重复 ≥ 1000 次 | 漂移率是否高于"顺序无关"的偶然水平 |
| **单 agent 对照** | 同一任务用单 agent 跑，测同一定义下的"漂移"率 | agent 间交互是否**加剧**了漂移 |
| **显式指令对照** | 主动下达换目标指令，测合法切换的率 | 用来标定"合法切换"的量级 |

**主检验 = 置换零分布**（因为它直接回答"顺序/交互结构是否产生了超出偶然的偏移"）。

### 3.4 样本量与功效

- **目标效应量**：先按"漂移率高于零分布均值 10 个百分点"作为最小可检测效应（MDE），保守取功率 0.8、α = 0.05
- **先行估算**：用 P1 的 100 轮预实验数据估方差，再反推所需轨迹段数
- **明确记录**：最终 n、功效、MDE——**不做事后功效辩护**

### 3.5 分层分析（RQ2 的落点）

按维度切分，看漂移在哪些条件下最高：

- **框架**：CAMEL（role-play）vs AutoGen/MetaGPT（任务型）
- **拓扑**：星型（有 orchestrator）vs 链型 vs 全连
- **轮次位置**：漂移是否集中在早期 handoff（线索：MasDrift 报告 **71.9% 约束丢失发生在第 1 次 handoff**，`2608.07556`，**未核实**——若复现则是一个强结论）
- **任务类型**：长程 vs 短程；强约束 vs 弱约束

## 4. P3：可观测信道下的检出上界

- **问题**：不看人工标签，只看 agent 之间**实际传递的内容**（消息、工具调用、状态），能否检出漂移？
- **做法**：用 P1/P2 的人工标签做真值，训练一个**弱监督分类器**（特征：语义原子序列的 n-gram / 嵌入距离 / 转移统计），报告 **单步定位 F1**
- **必带基线**：
  1. **随机基线**
  2. **相邻轮基线**（只看第 $k$、$k+1$ 轮）——**这条是硬性要求**，用来预防重蹈 DriftHunter 覆辙
  3. **跨轮累积**（DriftHunter 式）
- **判读**：若"相邻轮基线"≈"跨轮累积"，说明**累积不必要**，方法层要重新设计（这正是 DriftHunter 未做而该做的对照）

## 5. 资源估算（**含"是否该租服务器"的明确判断**）

### 5.1 结论：探针阶段**不需要多卡服务器**

| 阶段 | 实际算力需求 | 建议配置 |
|---|---|---|
| P1 标注一致性 | **纯人工 + 表格** | 不需要算力 |
| P2 生成轨迹 | LLM **API 调用**（或本地跑 7–8B 模型做消融） | **纯 API 即可**；若要本地跑消融，**1× 24GB 消费级卡足够** |
| P2 统计检验 | **CPU**（置换检验 1000 次） | 笔记本即可 |
| P3 弱监督分类器 | **CPU / 单卡**（小模型、小数据） | 单卡即可 |

**唯一的租服务器理由**：若要做**大规模本地模型消融**（多个开源模型 × 多种拓扑 × 多种子），才需要算力。但这属于**方法期**，不是探针期。

### 5.2 建议的资源决策顺序

1. **先定稿探针设计**（本文件）→
2. **先用 API + 一张消费卡跑 P1 + P2 预实验**（100 轮量级）→
3. **根据预实验的真实瓶颈**再决定租什么：若是 API 成本瓶颈 → 租单卡自托管；若是并行种子数瓶颈 → 租多卡
4. **不要在没有探针数据前租多卡**——避免"租了 4 卡只用来发 API 请求"

### 5.3 预算项（需独立确认）

- LLM API 预算（生成轨迹 + 标注辅助）
- 人工标注工时（**≥ 2 名标注者 × 2 轮**，这是最硬的成本）
- 服务器（**暂估 0**，待 5.2 第 3 步）
