# Week 1 五人任务清单

> 项目：InflMem / Agent-Induced Drift  
> 周期：第 1 周（5 个工作日）  
> 本周目标：从零搭出一个**可观测、可回放的最小闭环**，证明“agent 推荐被接受后，memory 可能把 compliance 写成 preference”。  
> 本周不追求显著结果，只追求：数据能进、事件能记、memory 能写、指标能算、周五能 demo。

---

## 0. 本周成功标准

周五结束时，团队必须能演示下面这条链路：

```text
MemoryCD 20 个用户
        ↓
1 个用户 × 2 个 session 的合成交互
        ↓
naive writer / provenance writer
        ↓
MemoryRecord（含来源、exposure、confidence）
        ↓
MemoryBackend add / search / snapshot
        ↓
CMR、SFB 等指标输出
```

周五 demo 的最低验收：

- [ ] `pilot_users.jsonl` 至少有 20 个用户，字段和 MemoryCD 对得上。
- [ ] 能生成 1 个用户 × 2 个 session 的 `InteractionEvent`。
- [ ] 同一条交互分别经过 naive writer 和 provenance writer，产出不同的 `MemoryRecord`。
- [ ] 至少一个真实 memory adapter 能 `add` / `search`，其他 adapter 可以是 skeleton。
- [ ] `metrics.py` 能对固定 fixture 算出 CMR / SFB，并有单元测试。
- [ ] `run_pilot.py` 能一条命令跑完最小链路，输出 `metrics.json`。
- [ ] 三个 schema 完成 v1 评审并冻结。
- [ ] Week 2 的 Gate 1 实验配置已经写好，不临时拍脑袋。

> 本周唯一允许的“跑不通”：外部依赖（HF 下载、Mem0/Letta 安装）被网络或环境阻塞。此时必须保留 mock adapter 和 blocker 记录，不能停工。

## 3. 每人每日任务

### P1 — Lead / 因果与评测

**D1：定方向和边界**
- 主持 60 分钟 kickoff，逐条确认：
  - 研究问题不是“记忆漂移一般性问题”，而是“agent 诱导的 compliance 被写成 preference”。
  - 本周只做最小闭环，不做完整 benchmark。
  - 五个人的接口和依赖。
- 读 AcCoRD、MemoryCD、CALMRec、CAPTURE、ULSPB 的 abstract / method / experiment。
- 输出一页 `docs/kickoff.md`：目标、非目标、风险、本周决策。

**D2：写问题定义**
- `docs/problem.md`：
  - compliance 与 internalization 的定义。
  - 一个具体例子：用户接受蓝色耳机 ≠ 用户偏好蓝色。
  - 三个 RQ。
- `docs/causal_dag.md` v0：
  - 节点：真实偏好、agent action、exposure、acceptance、memory write、retrieval、未来推荐、用户反馈。
  - 标出混杂路径和需要控制的反事实。

**D3：定指标与评审 schema**
- `docs/metrics.md` v0：每个指标写清定义、输入、归一化方式、失败模式。
- 主持 schema review，逐字段问：
  - 这个字段是 agent 可见还是 evaluator 可见？
  - 这个字段能否支持反事实回放？
  - 这个字段是否泄露 hidden state？
- 形成 `docs/decisions.md` 的第一条决策记录。

**D4：定 pilot 协议**
- 写 `docs/pilot_protocol.md`：
  - 用户数、session 数、seed、模型、memory budget。
  - naive 与 provenance 的对照方式。
  - 本周只验证“可测”，不验证“显著”。
- 写 Week 2 Gate 1 配置草案：
  - 20 用户 × 5 sessions。
  - 3 个 memory 系统 × 2 个 writer × 5 seeds。
  - 主指标 CMR，副指标 SFB / AL / CR。

**D5：Demo 与复盘**
- 主持 60 分钟 demo，按第 7 节脚本走。
- 记录三个问题：哪里断了、哪里定义不清、下周谁补。
- 输出 `docs/week1_review.md` 和 Week 2 任务草案。

**P1 本周验收**
- [ ] `problem.md`、`causal_dag.md`、`metrics.md`、`pilot_protocol.md` 均可读。
- [ ] DAG 能解释“为什么 acceptance 不能直接当 preference”。
- [ ] schema v1 有 P1 签字。
- [ ] Week 2 Gate 1 配置不需要再补关键定义。

### P2 — Sim / Data

**D1：把数据拿下来**
- 从 Hugging Face 下载 MemoryCD，记录：
  - 数据集版本、下载时间、文件 checksum。
  - 用户数、item 数、域、交互字段。
- 检查 5 个用户的原始记录，画出字段关系。
- 输出 `docs/data_notes.md` 第一版。

**D2：Loader 和 catalog**
- 写 `src/inflmem/data/memorycd.py`：
  - 读取用户、item、interaction。
  - 统一字段名，保留原始 ID。
- 建 catalog：
  - 先做 Electronics + Books 两个域。
  - 字段：`item_id`、`title`、`category`、`attributes`、`price`。
- 写最小单测：能读 1 个用户、能按 item_id 查 catalog。

**D3：20 用户子集**
- 产出 `data/processed/pilot_users.jsonl`：
  - 20 个用户，覆盖至少 2 个域。
  - 每个用户至少 3 条历史交互。
- 产出 `data/processed/manifest.json`：
  - 版本、用户数、item 数、checksum、生成脚本 commit。
- 做一次缺失值检查，把不能用的用户剔除并记录原因。

**D4：Simulator v0**
- 写 `src/inflmem/sim/influence_sim.py`：
  - 隐藏状态 `theta_t`：color / size / price_sensitivity / brand。
  - 每 session 以 p=0.1 产生外生冲击。
  - agent 推荐后，用户以概率接受；接受后以概率 internalize。
- 先生成 1 个用户 × 5 sessions 的 `InteractionEvent` JSONL。
- 每个事件必须有：`event_id`、`user_id`、`session_id`、`agent_action`、`user_response`、`exposure`、`timestamp`。

**D5：Smoke 和数据 QA**
- 跑 1 用户 × 2 sessions 的 smoke，确认 P3/P4/P5 都能消费。
- 检查事件顺序、session 边界、exposure 字段是否完整。
- 输出 `reports/data_qa_v0.md`。

**P2 本周验收**
- [ ] loader 能在干净环境复现。
- [ ] 20 用户子集和 manifest 已生成。
- [ ] simulator 能稳定生成 1 用户 × 5 sessions。
- [ ] 所有事件符合 `InteractionEvent` schema。
- [ ] 原始数据没有提交进 git。

### P3 — Memory

**D1：列接口需求**
- 读 Mem0、Letta、A-MEM 的 add/search/update 接口。
- 列出三者的差异：作用域、metadata、时间、删除、快照。
- 写 `docs/memory_backends.md` v0。

**D2：定义 MemoryBackend**
- 写 `src/inflmem/memory/base.py`：
  - `add(record)`
  - `search(query, user_id, top_k)`
  - `get_all(user_id)`
  - `delete(memory_id)`
  - `snapshot(user_id)`
  - `restore(snapshot)`
- 写 `MockMemory`，用内存 dict 实现。
- 加单测：add/search/delete/snapshot 的基本行为。

**D3：接第一个真实 adapter**
- 优先接 Mem0；如果安装或 API 阻塞，接 Letta 或 A-MEM。
- 统一输入输出为 `MemoryRecord`，不要泄露后端原始格式。
- 输出 `docs/adapter_alignment.md`：字段映射、缺失字段、绕过方式。

**D4：日志与反事实回放**
- 实现事件日志：
  - 每次 add/search 记录输入、输出、耗时、memory_id。
- 实现 `snapshot` / `restore`：
  - 保存某个 session 结束后的 memory 状态。
  - 支持删除一条 memory 后重放同一 query。
- 写 `counterfactual_replay` 雏形，不要求做因果估计。

**D5：Smoke 和对齐报告**
- 用 P2 的 1 用户 × 2 sessions 数据跑：
  - 第一 session 写入。
  - 第二 session 检索。
- 检查 memory 是否跨 user 泄漏。
- 输出 `reports/memory_smoke_v0.md`。

**P3 本周验收**
- [ ] `MemoryBackend` 接口冻结。
- [ ] 至少一个真实 adapter 能 add/search。
- [ ] 事件日志能定位每条 memory 的来源事件。
- [ ] snapshot / restore 可用。
- [ ] 有 user scope 的隔离测试。

### P4 — Method

**D1：读 user simulator 和 prompt**
- 读 AcCoRD 的 user simulator、preference dynamics、goal dynamics。
- 列出本周需要的状态字段：当前偏好、历史偏好、exposure、acceptance、internalization。
- 输出 `docs/writer_requirements.md`。

**D2：写两个 writer**
- `naive_writer`：
  - 看到“用户接受了蓝色耳机”，写成 “User prefers blue.”
- `provenance_writer`：
  - 写成 “User accepted blue after agent recommendation; prior preference black; may be compliance.”
  - 保留 `source_event_ids`、`exposure`、`influence_prob`、`confidence`、`validity`。
- 用 20 条手写或合成事件做 fixture，产出 20 条 `MemoryRecord`。

**D3：Influence 规格**
- 写 `docs/influence_model.md` v0：
  - exposure 强度如何定义。
  - acceptance 与 internalization 如何区分。
  - 哪些是观测变量，哪些是隐藏变量。
- 与 P2 对齐 simulator 的概率参数，不要各写一套。

**D4：Writer v0 接入**
- 把 writer 接到 P2 的事件流，输出标准 `MemoryRecord`。
- 做 3 个 prompt 变体：
  - 严格 provenance。
  - 中等 provenance。
  - 纯摘要。
- 记录每个变体的输出差异，不急着选“最好”的。

**D5：Prompt 对比**
- 用同一批 20 条事件跑 3 个变体。
- 输出 `reports/prompt_v1.md`：
  - 哪些字段稳定。
  - 哪些模型会漏掉 provenance。
  - 哪个 prompt 作为 Week 2 默认。
- 给 P5 提供固定的 writer 输出，供指标测试。

**P4 本周验收**
- [ ] naive / provenance 两个 writer 都能产出合法 JSON。
- [ ] provenance writer 不把 acceptance 直接写成 preference。
- [ ] 20 条 fixture 的输出可被 P3 的 MockMemory 接收。
- [ ] influence 规格与 P2 的 simulator 参数一致。
- [ ] 有 3 个 prompt 变体的对比记录。

### P5 — Eval / Analysis

**D1：定指标输入**
- 读 CMR、SFB、AL、OUR、CR 的定义和相近论文的实现。
- 列出每个指标需要的字段：
  - 真实偏好、memory 中的偏好、exposure、acceptance、推荐结果。
- 输出 `docs/metric_inputs.md`。

**D2：Metrics 骨架**
- 写 `src/inflmem/eval/metrics.py`：
  - `compliance_misattribution_rate`
  - `self_fulfilling_bias`
  - `adoption_lag`（可先返回占位）
  - `overuse_rate`（可先返回占位）
  - `recommendation_quality`
- 写 golden fixtures：
  - 一个明显误写的例子。
  - 一个正确 internalization 的例子。
  - 一个没有 exposure 的例子。
- 每个指标至少一个单测。

**D3：Run logging**
- 定 `run_id = YYYYMMDD_method_model_dataset_seed`。
- 每次 run 写：
  - `config.yaml`
  - `events.jsonl`
  - `memories.jsonl`
  - `metrics.json`
  - `stdout.log`
- 写 `scripts/run_pilot.py` 的参数解析和空壳。

**D4：串最小链路**
- 接 P2 的事件、P3 的 memory、P4 的 writer。
- 先不用真实 LLM 也能跑：用 fixture 或 mock。
- 输出 `runs/<run_id>/metrics.json`。
- 如果链路断了，明确记录是哪一方的接口问题。

**D5：第一张图和 pilot 报告**
- 用 20 条 fixture 或 1 用户 × 2 sessions 的结果画：
  - CMR：naive vs provenance。
  - 横轴可以是 exposure 强度，纵轴 CMR。
- 写 `reports/pilot_v0.md`：
  - 这周测了什么。
  - 结果是否只是 pipeline sanity check。
  - 下周 Gate 1 还缺什么。
- Demo 时展示图和原始 memory 记录，不只展示汇总数字。

**P5 本周验收**
- [ ] CMR / SFB 有明确公式和单测。
- [ ] `run_pilot.py` 能一条命令跑通最小链路。
- [ ] 每次 run 的输入、输出、配置可追溯。
- [ ] 有一张能看懂的第一版图。
- [ ] 报告明确区分“链路验证”和“科学结论”。

## 6. 依赖关系

```text
P2: MemoryCD loader + InteractionEvent
        │
        ├──► P4: writer 需要事件字段
        │
        └──► P5: metrics 需要 exposure / acceptance / hidden state

P3: MemoryBackend + MemoryRecord
        │
        ├──► P4: writer 输出必须能被 memory 接收
        │
        └──► P5: 指标需要检索结果和 memory 内容

P1: schema + metric spec
        │
        └──► 所有人：字段定义和评测口径
```

**关键路径：**
1. P2 的事件 schema。
2. P3 的 memory 接口。
3. P4 的 writer 输出。
4. P5 的 runner 和指标。
5. P1 的 schema 签字。

任何一项延迟超过半天，P1 必须在当日 blocker sync 中决定：降级、绕过，还是砍掉。

## 7. 周五 Demo 脚本（30 分钟）

1. **P2（5 分钟）**：打开 `pilot_users.jsonl`，展示 20 个用户和一个用户的 2 个 session。

3. **P4（5 分钟）**：同一条交互，naive 写成 “User prefers blue.”，provenance 写成“接受推荐，可能是 compliance”。
4. **P5（5 分钟）**：展示 `metrics.json` 和第一张 CMR 图，声明这只是 sanity check。
5. **P1（5 分钟）**：讲清楚本周验证了什么、没验证什么、Week 2 Gate 1 怎么跑。
6. **全员（5 分钟）**：定三个下周阻塞项和负责人。

**Demo 通过标准：**
- 不是 PPT 讲架构，而是实际跑出文件。
- 能指出一条具体 memory 的来源事件。
- 能说清楚为什么 naive writer 可能错。
- 能说清楚下周什么结果会让项目继续或转向。

## 9. Week 2 的入口条件

只有满足下面条件，才进入 Gate 1：

- [ ] 20 用户 × 5 sessions 的 simulator 配置已定。
- [ ] naive 与 provenance 两个 writer 都能稳定输出。
- [ ] 至少一个真实 memory adapter 跑通。
- [ ] CMR / SFB 有可执行实现和单测。
- [ ] `run_pilot.py` 能一条命令复现一次 run。
- [ ] 团队对“什么叫 compliance 被写成 preference”没有分歧。

Gate 1 的判定仍然按总计划执行：**naive CMR ≥ 20%，且 provenance 相对下降 ≥ 30%**；否则调整 influence 强度或换 domain，不硬做。
